          How the time adds up

          Before a page can start arriving, a browser waits for a chain of round trips. A round trip is a message going to the other end and the answer coming back, and its length, the round-trip time or RTT, is set mostly by distance: light in fibre covers about 200 km in a millisecond, so every 100 km between the two ends adds at least 1 ms to the round trip, before any router or queue adds its own and because cables do not run straight. Each step below waits for the one before it.

          1. The lookup. The browser asks a resolver for the address behind the name. If the browser, the operating system or the resolver already has the answer, that costs nothing or one short round trip. If not, the resolver asks a root server, a top-level-domain server and the domain’s own name server in turn (RFC 1034), a round trip each. A resolver usually has the root and top-level servers cached, so the common slow case is one question to the domain’s name server.
          2. The TCP handshake. SYN goes out and SYN-ACK comes back. The browser’s own acknowledgement travels with its next message, so the connection costs one round trip before the request can be sent.
          3. The TLS handshake. TLS 1.2 needs two more round trips before the browser can send the request; TLS 1.3 (RFC 8446) needs one. When a connection resumes an earlier session, TLS 1.2 needs one, and TLS 1.3 can send the request in the very first flight as 0-RTT early data. A server cannot tell a replayed early request from the original, so 0-RTT is only safe for requests that change nothing.
          4. The request. One more round trip, plus however long the server takes to build the response. Everything up to the first byte of the answer is what the browser’s tools call the time to first byte.
          5. The rest of the response. The server cannot send everything at once. TCP starts with a window of ten segments, about 14.6 kB (RFC 6928), and doubles it every round trip while the acknowledgements come back (RFC 5681). QUIC’s first flight is about the same size (RFC 9002), so the calculator uses one number for every stack. A 150 kB page therefore needs three more round trips after the first flight, even on a fast link. On a slow link the bytes themselves take longer than that, and the calculator uses whichever is longer.

          Why TLS 1.3 and HTTP/3 are faster

          They are not faster at moving bytes. They ask for fewer round trips before the request can go. TLS 1.3 halves the encryption handshake from two round trips to one. HTTP/3 (RFC 9114) runs over QUIC (RFC 9000), which sets up the connection and the encryption in a single round trip where TCP and TLS 1.2 take three, and on a resumed connection can send the request with the first packet. The saving is a fixed number of round trips, so it is worth the most where the round trip is longest: two round trips are 20 ms at 10 ms and 600 ms at 300 ms. Try the “Phone on 4G, far away” start and compare the stacks in the table.

          The biggest lever is the first slider. A CDN or a server in your visitor’s own region shortens the round trip itself, and every round trip in the list above gets cheaper at once.

          Why a small page is fast

          A page that fits in the first flight, about 14.6 kB, arrives with the first byte and waits for nothing. Every doubling of the page size after that costs one more round trip, which is why the first few kilobytes are the expensive ones and why compression, fewer scripts and smaller images pay off more on a long round trip than on a short one.

          What this leaves out

          This is a teaching model, built to show the shape of the cost, not to predict one particular site. It assumes a steady round trip, no lost packets, a single resource, a window that doubles every round trip, and a server that starts sending as soon as it has the request. It leaves out redirects, which add whole new lookups and connections; HTTP/2 and HTTP/3 carrying many resources over one connection; the certificate checks a browser may make; delayed acknowledgements and what a lost packet does to the window; and the time spent parsing and drawing the page. To measure a real page, open the Network panel in your browser’s developer tools and read the Timing tab of the first request, or run this:

          curl -so /dev/null https://example.com/ -w '
dns         %{time_namelookup}s
connect     %{time_connect}s
tls         %{time_appconnect}s
first byte  %{time_starttransfer}s
total       %{time_total}s
'

          curl prints each time as the total elapsed since the start, so what one step cost is its time less the one before it.

          • RFC 6928, Increasing TCP’s Initial Window: the ten-segment first flight.
          • RFC 5681, TCP Congestion Control: slow start and the window doubling every round trip.
          • RFC 8446, TLS 1.3: the one-round-trip handshake and 0-RTT early data.
          • RFC 9000, QUIC and RFC 9114, HTTP/3: the transport and encryption handshake in one round trip.
          • RFC 9002, QUIC Loss Detection and Congestion Control: its initial window.
          • RFC 1034, Domain Names: Concepts and Facilities: how a resolver finds a name.
          • Time to First Byte on web.dev: what the browser counts into it.
