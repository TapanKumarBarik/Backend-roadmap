Caching Architecture & Stampede Protection Explained

1. The Thundering Herd / Cache Stampede

When high-frequency keys (e.g. homepage headlines or trending products) expire, hundreds or thousands of simultaneous client queries encounter a cache miss at the exact same millisecond. Each worker rushes the database to compute the same query, crashing database connection pools.

2. Distributed Mutex Locking (Redis SETNX)

On a cache miss, requests attempt to acquire an exclusive lock: SET key:lock uuid NX PX 5000. Only the lock winner queries the database and populates the cache. Other concurrent threads sleep for 50ms and retry reading from the warm cache, dropping database load from 1,000 queries to 1.

3. XFetch Probabilistic Early Expiration

Proposed by Vattani et al., XFetch evaluates: -beta * delta * ln(rand()) > TTL - now, where $\delta$ is the database computation duration. As the key nears expiration, the probability of an async background pre-refresh increases smoothly, eliminating waiting stalls for all incoming users.

4. Cache-Aside vs. Write-Through vs. Write-Behind

Cache-Aside gives full control to the application but requires explicit invalidation on updates. Write-Through eliminates stale data but incurs write latency overhead. Write-Behind absorbs heavy write bursts in RAM but risks data loss if the cache node crashes before flushing dirty writes to disk.
