    Token Bucket vs. Leaky Bucket: Key Differences

    Both algorithms enforce rate limits, but they serve fundamentally different architectural purposes:

    • Token Bucket (Burst Tolerant): Tokens are deposited into a bucket at a fixed rate $r$ up to capacity $b$. Each incoming request consumes 1 token. If the bucket has tokens, requests are processed immediately with zero queuing latency. This makes Token Bucket ideal for user-facing API gateways (e.g. AWS API Gateway, Stripe) where legitimate users frequently trigger bursts (e.g. opening a dashboard that fires 8 parallel queries).
    • Leaky Bucket (Traffic Shaper): Requests enter a FIFO queue (the bucket) of capacity $b$. The queue drains to downstream services at an unvarying, strictly constant rate $r$. If the queue is full, incoming packets are dropped. This transforms jagged spikes into a perfectly smooth stream, protecting fragile legacy databases and downstream third-party APIs from sudden concurrency surges.
    • Sliding Window Counter: Computes the request rate over a rolling time window, eliminating boundary-burst vulnerabilities inherent in naive Fixed Window counters without requiring unbounded memory.

    HTTP Headers & Best Practices

    When an API gateway throttles a client, standard production architectures return HTTP 429 Too Many Requests along with RFC standard rate limiting headers:

    • Retry-After: 5 — advises the client how many seconds to wait before retrying.
    • X-RateLimit-Limit: 100 — maximum allowed requests per window.
    • X-RateLimit-Remaining: 0 — remaining tokens/requests in current window.
    • X-RateLimit-Reset: 1732100000 — UTC epoch timestamp when the quota resets.
