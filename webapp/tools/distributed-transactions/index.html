2PC vs. Saga Pattern: The Architectural Trade-offs

1. Two-Phase Commit (2PC) & Blocking Locks

In 2PC, a central coordinator asks participants to prepare (locking row data). If all participants agree, it sends GLOBAL_COMMIT. While guaranteeing strict ACID serializability, 2PC holds database locks across network boundaries. If the coordinator or network crashes during Phase 2, participants remain blocked holding locks, severely limiting throughput.

2. Saga Pattern & Compensating Transactions

A Saga replaces distributed locking with a sequence of local ACID transactions. Each microservice commits locally immediately and releases its locks. If a subsequent step fails, the saga executes compensating transactions in reverse order (e.g. issuing a credit card refund or unreserving stock), trading isolation for high availability and linear scalability.

3. Orchestration vs. Choreography

Orchestrated Sagas use a dedicated workflow coordinator (like Temporal or AWS Step Functions) that explicitly commands each service and handles failure routing. Choreographed Sagas use event pub/sub (Kafka/RabbitMQ) where services publish and subscribe to domain events without a central coordinator.

4. Semantic Idempotency Requirements

Because network retries can trigger duplicate requests, both forward transactions and compensating actions in a Saga must be strictly idempotent (using unique idempotency keys) and handle out-of-order delivery gracefully.
