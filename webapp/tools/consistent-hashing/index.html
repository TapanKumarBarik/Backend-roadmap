    Why Modulo Hashing Fails at Scale

    A naive approach to distributing cached data across $N$ database or cache servers uses the modulo operator: serverIndex = hash(key) % N. While this works fine when the cluster never changes, adding or removing a single node changes the denominator from $N$ to $N+1$ or $N-1$. As a result, almost every existing key hashes to a completely different index—invalidating roughly $N / (N+1)$ (typically 80% to 90%+) of all cached data instantly, triggering a catastrophic cache stampede on backend databases.

    The Consistent Hash Ring Solution

    Consistent hashing (introduced by Karger et al.) solves this by mapping both servers and keys onto a shared continuous circular integer space (such as a 32-bit integer range $[0, 2^{32} - 1)$):

    • Each physical server is assigned one or more points on the ring using its identifier (e.g. hash("server-A")).
    • To find which server owns a key, the client hashes the key and traverses clockwise along the ring until it encounters the first server token.
    • When a new server joins, it only takes ownership of keys that lie in the segment immediately preceding its token. Keys on other parts of the circle remain completely untouched, ensuring that on average only $1/N$ of the data needs to migrate.

    Why Virtual Nodes (Vnodes) are Essential

    If each physical server has only one token on the ring, random chance causes non-uniform spacing, creating huge gaps where one server handles 50%+ of all requests while others sit idle. Virtual Nodes (vnodes) assign multiple tokens to each physical server (e.g. server-A#v0, server-A#v1, … server-A#v14). By interleaving hundreds of tokens around the perimeter, the law of large numbers guarantees that keys are distributed smoothly and evenly across all machines.
